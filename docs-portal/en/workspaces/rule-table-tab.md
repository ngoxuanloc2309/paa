## 1. Purpose & Operational Role

The **Rule Table** (`Ctrl+4`) is the deterministic execution ledger of **SynaptiX IDE**. Whenever an engineer presses `F7` (**Compile Rules**) on the [Logic Graph Canvas](/workspaces/logic-graph-tab), the visual block topology is lowered into an ordered array of flat, constant-time **Event–Condition–Action (ECA)** rules indexed `0..99` (displayed as `R1..R100`) alongside compiled fieldbus, cloud, and stateful function block schedules.

During plant commissioning, Factory Acceptance Testing (FAT), and safety audits, the **Rule Table** serves four essential engineering purposes:

1. **Deterministic Compilation Verification:** Inspecting the exact stage-by-stage lowered representation (`Trigger`, `Comparator / Threshold`, `Guard`, `Action`) that the **SynaptiX Runtime** evaluates sequentially on every scan cycle.
2. **Hardware Rule Budget Governance (`0..100` Rules):** Tracking total rule consumption against the deterministic **100-rule hardware capacity**, including multi-rule expansions generated by stateful IEC macro blocks (`TON`, `TOF`, `TP`, `CTU`, `CTD`).
3. **Unified Subsystem Auditing:** Reviewing all four compiled runtime schedules—**Logic Rules**, **Modbus Master**, **MQTT Services**, and **Function Blocks**—in tabular form without panning across large visual sheets.
4. **Rule Optimization & Hardware Readback:** Executing **Deduplicate Rules** to eliminate redundant logic branches, toggling individual rules active/disabled, exporting audit CSVs, or uploading live rule tables directly from field hardware via `F6`.

## 2. Visual Layout & Controls Reference

![SynaptiX Compiled Rule Table Workspace](/images/synaptix_rule_table.png)

The **Rule Table** combines a top **Hardware Quota Header**, **4 Subsystem Sub-Tabs**, an operational **Filter & Optimization Toolbar**, the high-density **ECA Rule DataGrid**, and a collapsible bottom **Logic Flow Inspector**.

### 2.1. 100-Rule Hardware Budget Reference

The SynaptiX Controller provides a deterministic budget of **100 rule slots (`R1..R100`)**. Upon compilation (`F7`), canvas blocks consume slots according to predictable hardware quotas:

| Canvas Block Type | Rule Slots Consumed | Operational Notes |
| :--- | :---: | :--- |
| **Standard Logic Chain** (`Input -> Trigger -> Action`) | **1 Rule** | Occupies 1 standard execution slot. |
| **Timer Blocks** ([`TON`](/blocks/ton), [`TOF`](/blocks/tof), [`TP`](/blocks/tp)) | **2 Rules** | 1 rule for time accumulation, 1 rule for output actuation. |
| **Counter Blocks** ([`CTU`](/blocks/ctu), [`CTD`](/blocks/ctd)) | **4 Rules** | Includes rules for edge counting, reset, and threshold comparison. |
| **Modbus Master & MQTT Channels** | *0 Rule Slots* | Managed separately in dedicated peripheral tables. |

### 2.2. Toolbar Controls, Sub-Tabs & Hardware Budget Bar

| Control / Sub-Tab | Location | Function & Operational Behavior |
| :--- | :--- | :--- |
| **Hardware Rule Budget Bar** (`0..100` / `%`) | Top Header Right | Displays real-time rule utilization (`ActiveCount / 100` and `MemoryUsagePercent`) so engineers can verify deterministic scan headroom at a glance. |
| **New Rule / Edit on Canvas** | Top Header Left | Creates a direct tabular rule entry or jumps straight to the corresponding visual network in the [Logic Graph Canvas](/workspaces/logic-graph-tab) (`Ctrl+2`). |
| **Sub-Tab 1: `Logic Rules`** | Primary Sub-Tab | Lists all lowered ECA rules (`R1..R100` corresponding to runtime slots `0..99`) evaluated in strict ascending index order. |
| **Sub-Tab 2: `Modbus Master`** | Secondary Sub-Tab | Summarizes all compiled RS-485 `MB_READ` polling channels and `MB_WRITE` actuation commands (Slave ID, Function Code, Register, Interval, Local Tag). |
| **Sub-Tab 3: `MQTT Services`** | Secondary Sub-Tab | Summarizes all compiled `MQTT_PUB` outbound telemetry topics/QoS/payload templates and `MQTT_SUB` inbound JSON key bindings. |
| **Sub-Tab 4: `Function Blocks`** | Secondary Sub-Tab | Lists active stateful timer and counter block instances (`TON`, `TOF`, `TP`, `CYCLE_TIMER`, `CTU`, `CTD`) with their preset (`PT`/`PV`) bindings. |
| **Status Filter Pills** (`All` / `Active` / `Disabled`) | Filter Toolbar | Isolates enabled production rules or temporarily muted commissioning rules. |
| **Deduplicate Rules** | Filter Toolbar | Scans the entire rule set for identical `Trigger + Comparator + Guard + Action` signatures, removes duplicates, and cleanly re-indexes `R1..Rn`. |
| **Upload from Device (`F6`) & Export CSV** | Filter Toolbar | Reads the active rule table back from a connected **SynaptiX Edge Controller** or exports a complete FAT cause-and-effect CSV report. |
| **Instant Search Box** | Filter Toolbar Right | Filters rules instantaneously by Rule ID (`R12`), Tag Name (`AI0`), Alias, Macro badge, or natural-language Narrative text. |

### 2.3. Logic Rules DataGrid Columns Reference

| Column Header | Content Format | Engineering Interpretation |
| :--- | :--- | :--- |
| **`Enabled`** | Interactive Checkbox | Enables or mutes execution of the rule slot (`0..99`) without deleting its configuration or breaking visual wires. |
| **`ID`** | Monospace Index (`R1`..`R100`) | Deterministic scan evaluation order. Rule `R1` (slot `0`) always executes before `R2` (slot `1`) within the same scan cycle. |
| **`Trigger` & `Comparator / Threshold`** | Stage 1 & Stage 2 Summary | Displays the monitored source tag, edge/timing mode (`ON_RISE`, `ON_FALL`, `ON_CHANGE`, `INTERVAL`, `TIME_WINDOW`), dwell filter (`ForMs`), relational operator (`==`, `!=`, `>`, `>=`, `<`, `<=`, `BETWEEN`), and typed threshold (`INT32` or `REAL`). |
| **`Guard`** | Stage 3 Safety Interlock | Displays the permissive interlock tag and required state (`== 1` normal or `== 0` inverted), or `--` when unguarded. |
| **`Action`** | Stage 4 Output Command | Displays the deterministic command (`SET_TAG`, `TOGGLE_TAG`, `INC_COUNTER`, `WRITE_REMOTE`, `SEND_ALARM`, `LOG_EVENT`), target tag, and write parameter. |
| **`Macro`** | Source Attribution Pill | Identifies whether the rule was expanded from a higher-level IEC macro block (for example, `TON #1`, `CTU #2`) or a direct pipeline. |
| **`Narrative`** | Plain-Language Specification | Auto-generated cause-and-effect sentence suitable for direct inclusion in plant commissioning documentation. |
| **`Actions`** | Row Action Icons | Provides one-click **Edit in Logic Graph** (centers the source nodes on Canvas) and **Delete Rule**. |
| **Bottom Logic Flow Inspector** | Collapsible Detail Strip | Renders the selected row's 4-stage pipeline (`Trigger → Comparator → Guard → Action`) as structured visual stage cards for rapid verification. |

## 3. Step-by-Step Operational Procedures

### Procedure 3.1: Auditing Lowered Rules & Hardware Budget After Compilation

1. Author or modify your control logic on the [Logic Graph Canvas](/workspaces/logic-graph-tab) (`Ctrl+2`) and press `F7` (**Compile Rules**).
2. Press `Ctrl+4` to switch to the **Rule Table**.
3. Inspect the **Hardware Rule Budget Bar** in the top-right corner to confirm total rule count is well within the **100-rule** capacity (`0..99`).
4. Click any row in the **Logic Rules** table to expand the bottom **Logic Flow Inspector** and verify its source tag, threshold type (`INT32` vs `REAL`), safety guard polarity, and target actuation tag.
5. Switch across the **Modbus Master**, **MQTT Services**, and **Function Blocks** sub-tabs to verify peripheral polling intervals and topic paths before deployment.

### Procedure 3.2: Optimizing Redundant Branches & Generating a Cause-and-Effect CSV

1. When merging multiple [Blueprints](/workspaces/blueprints-tab) or copied logic sheets, open the **Rule Table** (`Ctrl+4`) and click **Deduplicate Rules** on the toolbar.
2. **SynaptiX IDE** identifies any rules with identical trigger, threshold, guard, and action contracts, removes redundant slots, and re-sequences rule IDs cleanly.
3. Click **Export CSV** on the toolbar to save a complete tabular Cause-and-Effect matrix for customer sign-off and cabinet documentation binders.

## 4. Engineering Best Practices & Edge Cases

::: warning SEQUENTIAL SCAN ORDER DETERMINISM (`R1` → `R100`)
The **SynaptiX Runtime** evaluates enabled rules strictly in ascending order from slot `0` (`R1`) through slot `99` (`R100`) within every deterministic scan cycle. If Rule `R5` sets `DO0 = 1` and Rule `R12` sets `DO0 = 0` during the exact same scan cycle while both conditions are true, **last-writer-wins** applies within the output image buffer (`DO0` evaluates to `0` at end-of-scan). Always review rules targeting the same output coil by typing the tag name (for example, `DO0`) into the **Rule Table** search box.
:::

- **Accounting for Macro Expansion in Large Projects:** Because each `TON`/`TOF`/`TP` timer consumes **2 rule slots** and each `CTU`/`CTD` counter consumes **4 rule slots**, a project containing 10 timers and 5 counters utilizes `10 × 2 + 5 × 4 = 40` rule slots, leaving **60 slots** for direct ECA pipelines. Use the **`Macro`** column badge to trace which multi-rule group belongs to each visual block.
- **Non-Destructive Rule Muting During Commissioning:** Need to temporarily isolate an alarm horn or downstream conveyor interlock during sensor calibration? Uncheck the **`Enabled`** box on that row in the **Rule Table** and press `Ctrl+F5` to deploy—preserving all visual wiring on the canvas for instant re-activation after testing.
