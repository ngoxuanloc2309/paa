Grounded in IEC 61131-3 principles, SynaptiX IDE treats data types not as cosmetic UI labels, but as strict physical memory contracts paired with a deterministic Input State Machine (Bad-Data Defense) so that what an engineer sees on screen is always a 1:1 reflection of what executes inside the SynaptiX Edge Controller.

Strict Physical Data Types

Microcontrollers and industrial edge runtimes operate strictly on binary bit-patterns inside 32-bit memory slots. SynaptiX IDE enforces three physical data types across all workspaces:

1. BOOL — Single-Bit Binary State

  • Valid Domain: Strictly 0 (False / Low / Off) or 1 (True / High / On).
  • Applicable Tags: Mandatory and fixed for DI0..7, DO0..7, and VFLAG0..31.
  • UI Control Contract: Wherever a boolean constant is configured, SynaptiX IDE provides explicit binary state selectors (0 / 1) or normalizes boolean text keywords strictly to "0" or "1".

2. INT32 — 32-Bit Signed Two's Complement Integer

  • Valid Domain: Exact whole integers from -2,147,483,648 to +2,147,483,647 (-2^31 to 2^31 - 1).
  • Applicable Tags: Fixed for COUNTER0..7; selectable on AI0..3, VREG0..31, and VREG_RETAIN0..31.
  • Physical Ground Truth — Why 25.5 Cannot Exist in INT32: In two's complement integer hardware, every bit weight represents an exact power of two (2^0 = 1, 2^1 = 2, ..., 2^30). There are zero fractional bit positions. A decimal value such as 25.5 physically cannot be stored in an INT32 register without silent truncation (25) or fixed-point scaling (255 in 0.1 tenths). Because silent truncation causes dangerous discrepancies between what an engineer typed and what the controller compares at runtime, SynaptiX IDE strictly rejects non-zero fractional inputs (such as "25.5") on INT32 fields.

3. REAL — 32-Bit IEEE-754 Single-Precision Floating-Point

  • Valid Domain: IEEE-754 binary32 floating-point numbers (1 sign bit, 8 exponent bits, 23 mantissa fraction bits; ~7 significant decimal digits).
  • Applicable Tags: Selectable on AI0..3, VREG0..31, and VREG_RETAIN0..31 in the Tag Catalog.
  • Memory Representation: Stored lossless in the 32-bit tag slot via IEEE-754 bit-casting (SingleToInt32Bits) and always rendered in SynaptiX IDE with at least one explicit decimal place (for example, "25.0", "65.25") so engineers can visually distinguish REAL tags from INT32 tags at a glance.
[ Preventing Type-Mismatch Bugs Before Compilation ]

When you change a tag's data type in the Tag Catalog (for example, switching AI0 from INT32 to REAL), any connected COMPARATOR or ACTION blocks immediately adapt their constant validation rules to match the updated tag contract. NaN and Infinity bit patterns are automatically sanitized to "0.0".

1.3 Deterministic Execution Pipeline & Runtime Engine

Conventional edge gateways often suffer from a fatal architectural flaw: executing slow network sockets or serial bus retries on the same thread as local safety interlocks. A single unresponsive RS-485 slave or Wi-Fi packet retransmission can freeze discrete output actuation for hundreds of milliseconds.

The SynaptiX Edge Runtime solves this through a hybrid deterministic execution architecture: local input sampling, stateful function blocks, and up to 100 compiled Event-Condition-Action rules execute in a bounded, zero-allocation deterministic scan loop, while fieldbus and cloud transactions operate in decoupled non-blocking asynchronous worker queues.

Anatomy of a Complete Scan Cycle

Every deterministic scan cycle progresses through five ordered phases while exchanging snapshots atomically with background fieldbus and IIoT workers:

Step 01 • Latch
1. Input Snapshot

Synchronously latch discrete inputs DI0..7, sample analog sensors AI0..3, and freeze inbound fieldbus packets.

Step 02 • Update
2. Stateful Blocks

Accumulate monotonic timers (TON/TOF/TP), advance event counters (CTU/CTD), and execute SCALE conversions.

Step 03 • Evaluate
3. Rule Pipeline

Sequentially evaluate the 4-stage rule pipeline from Rule #1 to #100: INPUT → TRIGGER/CMP → GUARD → ACTION.

Step 04 • Commit
4. Output Commit

Synchronously drive physical relay terminals DO0..7, output PWM/PTO pulses, and persist retentive registers.

• Deterministic 10ms Closed Loop (100 Hz Hard Real-time) • Atomic boundary state exchange

Scan Determinism Guarantees

  • Input Image Freeze: Physical inputs (DI0..7, AI0..3) and inbound network values are latched at the top of the scan (Step 1). A tag's sampled input value never mutates mid-scan between Rule #0 and Rule #99.
  • Sequential Rule Ordering: Compiled rules execute strictly in ascending index order (Rule #0, Rule #1, ...) as displayed in the Rule Table (Ctrl+4).
  • Monotonic Timekeeping: All timers (TON, TOF, TP, CYCLE_TIMER) reference hardware monotonic ticks rather than wall-clock time, guaranteeing immunity against NTP/RTC clock adjustments during active timing intervals.

Non-Blocking Asynchronous Fieldbus & IIoT Workers

Network I/O inherently involves variable latency — an RS-485 sensor may take 25 ms to reply at 9600 bps, while a cellular/Wi-Fi TLS handshake or HTTP webhook may take 150–800 ms.

To guarantee that communication delays never stall local deterministic control, all six fieldbus and network function blocks execute asynchronously via lock-free internal request/completion queues:

Subsystem Visual Blocks Non-Blocking Decoupling Contract
RS-485 Modbus RTU Master MB_READ, MB_WRITE Trigger edges enqueue read/write transactions onto the dedicated RS-485 Master scheduler. The fast scan loop continues uninterrupted; once CRC-verified reply frames arrive, target VREG/VFLAG tags update atomically at the next scan boundary.
MQTT Telemetry & Control MQTT_PUB, MQTT_SUB MQTT_PUB snapshots tag values, expands payload macros (such as `{val1}`, `{ts}`), and hands the packet to the background TCP/TLS client. Inbound MQTT_SUB JSON messages are parsed in the background and staged for atomic tag commit at Step 1.

[ SEQUENTIAL SCAN ORDER DETERMINISM (`R1` → `R100`) ]

3.6 Atomic Deploy & Verification Gate

1. Purpose & Operational Role

The Atomic Deploy Workspace (Ctrl+6) is the release gate and non-volatile configuration commit engine of SynaptiX IDE. 2.2 Structural Wiring Rules

The SynaptiX IDE graph compiler enforces deterministic Function Block Diagram topology rules in real time as you drag wires on the canvas and during pre-deploy compilation (F7):

  1. Fan-Out Allowed (1:N), Fan-In Prohibited (1:1 per Input Port): A single output pin (such as INPUT.Out or TRIGGER.Out) may branch to multiple downstream blocks simultaneously. However, each individual target input port accepts at most one incoming wire.
  2. Directed Acyclic Graph (DAG) Enforcement: A node can never wire to itself, and circular wire loops within the same combinational network are rejected at compile time. To feed state back into a subsequent scan cycle, write to a virtual tag (VFLAG or VREG) via an ACTION block and read that tag from a separate INPUT node.
  3. Source & Sink Boundaries: INPUT nodes act strictly as signal sources (zero input pins), whereas ACTION nodes act strictly as terminal executors (zero output pins).
  4. Automatic Trigger Synthesis: Wiring INPUT → ACTION or INPUT → GUARD directly is permitted; the compiler automatically synthesizes the appropriate transition rule while preserving deterministic scan behavior.
  5. Single-Stage Guard & Trigger Discipline: TRIGGER cannot wire directly into another TRIGGER, and GUARD cannot chain directly into another GUARD (GUARD → GUARD) or loop back into TRIGGER. When combining multiple safety permissives, evaluate intermediate conditions into a VFLAG virtual flag tag.
  6. Smart Grid Auto-Alignment: Selecting a node on the canvas and clicking a compatible block in the toolbox spawns the new block 240 px to the right on the 20 px snap grid, aligns its primary input pin horizontally, and wires the connection automatically.

4.2 INPUT — Tag Source Signal Block

1. Synopsis & Execution Semantics

The INPUT block is the foundational signal entry point on the SynaptiX IDE Logic Graph Canvas. It binds a single physical I/O channel or virtual memory variable from the project Tag Catalog and exposes its live state onto the Out value connector on every scan cycle.

  • Deterministic Process Image Read: At the start of each scan cycle on the SynaptiX Runtime, hardware inputs are latched into an immutable process image snapshot. Every INPUT block referencing the same tag reads an identical, race-free value throughout that scan pass.
  • Zero-Overhead Lowering: INPUT does not consume a standalone execution slot; during compilation (F7), its bound tag index and physical data type (BOOL, INT32, or IEEE-754 REAL) propagate directly into downstream TRIGGER, COMPARATOR, SCALE, TON, CTU, or MQTT_PUB blocks.
  • Primary Industrial Use Cases: Reading discrete limit switches and E-Stop contacts (DI), monitoring coil feedback (DO), feeding raw 4–20 mA / 0–10 V sensor channels (AI) into calibration chains, and routing internal state flags (VFLAG) or retentive setpoints (VREG_R) across multi-rung control sequences.

2. Pinout & Signal Contract

INPUT acts strictly as a pure signal source and therefore exposes zero input connectors and one universal value output connector.

Pin Direction Signal Kind Data Type Description
Out Output Value / Data (IsEvent = false) Polymorphic (BOOL | INT32 | REAL) Emits the live value and tag metadata of the selected Tag. Capable of 1:N fan-out to multiple downstream blocks simultaneously.

5. Input Defense & Live Diagnostics

5.1 Bad-Data Defense (SmartInputParser)

To uphold the Visual Truth Guarantee—ensuring the Inspector display never contradicts physical memory—TagValueText enforces two-phase input resolution upon pressing Enter or leaving the field (LostFocus):

  • Digital (BOOL) Tags: The Inspector presents dedicated binary [ 0 ] and [ 1 ] buttons alongside tolerant parsing ("true", "on", "yes" → "1"; "false", "off", "no" → "0"). Unparseable text immediately reverts to the last committed "0" or "1".
  • Integer (INT32) Tags: Accepts signed 32-bit integers. Tolerates harmless .0 suffixes ("100.0" → normalized to "100"), but strictly rejects fractional decimals such as "25.5" or alphabetic strings ("abc"), reverting TagValueText to the exact integer stored in memory.
  • Floating-Point (REAL) Tags: Accepts both dot and comma decimal separators ("25,5" → "25.5") and automatically formats whole numbers with an explicit .0 suffix ("25" → "25.0") to confirm IEEE-754 32-bit float storage.

4.3 TRIGGER — Edge Detection & RTC Scheduling

1. Synopsis & Execution Semantics

The TRIGGER block converts continuous state signals, register values, monotonic system ticks, or Real-Time Clock (RTC) schedules into discrete execution event pulses (Out) that drive downstream GUARD, ACTION, TON, CTU, and fieldbus/IIoT blocks.

  • Single-Shot Edge Semantics: Unlike level-sensitive combinational gates that fire repeatedly on every scan pass while a sensor stays high, ON_RISE and ON_FALL compare the current scan's process image value against the previous scan's latched state, emitting one deterministic event pulse per valid transition.
  • Built-In Dwell / Debounce Filter (ForMs): Mechanical contacts, float switches, and noisy analog thresholds can be stabilized directly inside TRIGGER without consuming a separate timer block. Setting ForMs > 0 requires the transition condition to hold uninterrupted for at least ForMs milliseconds before firing.
  • Autonomous Time Modes: When configured as INTERVAL or TIME_WINDOW, TRIGGER operates autonomously from the internal monotonic clock or battery-backed RTC without requiring an upstream INPUT wire.
  • Primary Industrial Use Cases: Pushbutton and limit-switch edge detection, contact chatter suppression, periodic telemetry heartbeats (INTERVAL), daily/overnight shift scheduling (TIME_WINDOW), and compact analog threshold crossing rules.

4. Debounce Filtering & Pulse Firing Rules

The TRIGGER block produces single-scan execution pulses with deterministic timing:

  • Immediate Pulse (ForMs = 0): As soon as the edge condition (RISING, FALLING, or ANY_CHANGE) is detected, pin Out emits a single pulse of level 1, returning to 0 on the next scan cycle.
  • Debounce Dwell Filter (ForMs > 0): The input must remain stably at the new level for at least ForMs milliseconds before the pulse fires. Transient mechanical chatter or electromagnetic noise pulses shorter than ForMs are completely rejected.
  • Automatic Re-arming: After emitting a pulse, the block waits until the input signal returns to its opposing baseline before arming itself for the next edge event.

5. Input Defense & Live Diagnostics

5.1 Input Normalization & Clamping

  • RTC Hour & Minute Clamping: Entering out-of-bounds values in TimeStartHour / TimeEndHour or Minute fields automatically clamps values to valid 24-hour clock coordinates (00..23 and 00..59) and updates the formatted badge (HH:MM). Switching from Time Window Range back to Point-in-Time automatically synchronizes ThresholdHi = ThresholdLo.
  • Threshold Input Formatting: Inline ThresholdLoText and ThresholdHiText accept both dot and comma decimals ("25,5" → "25.5") via flexible numeric parsing and revert malformed text to the last valid numeric threshold on commit. Float equality (EQ / NEQ) applies a 1e-5 epsilon tolerance.

5.2 Canvas Badges in Simulator (F5) & Online Live Debug (F8)

  • Compact Mode Badge: Displays the active trigger signature directly on the node card—such as RISING EDGE (0 → 1), > 80 (500ms), Loop 1000ms, or 22:00 → 06:00—alongside • Connected: <TagName> when wired upstream.
  • Dwell Countdown & Fired Flash (F5): During Offline Simulation, TRIGGER displays real-time dwell countdown (SimDwellRemainingMs) while filtering an edge and flashes its status pill (TRIGGERED / WAITING PULSE) when an event pulse fires down the wire.

4.4 COMPARATOR — Relational & Threshold Evaluator

1. Synopsis & Execution Semantics

The COMPARATOR (CMP) block is a type-locked relational function that continuously compares an upstream tag or calibrated engineering value (In) against one or two reference thresholds (ThresholdLo, ThresholdHi) and outputs a pure BOOL truth signal (Out = TRUE or FALSE) on every scan cycle.

  • Strict Type-Locked Evaluation: The moment an upstream INPUT or SCALE block connects to In, COMPARATOR locks its arithmetic mode and Inspector input formatters to the upstream physical data type (INT32, IEEE-754 REAL, or BOOL).
  • Floating-Point Epsilon Safety: Direct bit-level equality checks on IEEE-754 floating-point sensor values notoriously fail due to binary representation rounding. When evaluating REAL (Float32) inputs, COMPARATOR automatically applies an industrial 1e-5 (0.00001) epsilon deadband on EQ (==) and NEQ (!=).
  • Combinational Level Output: Because Out is a continuous boolean value pin (IsEvent = false), it can feed a TRIGGER block for edge-triggered/debounced actuation, or wire directly into GUARD, ACTION, MQTT_PUB, HTTP_CLIENT, or TCP_CLIENT.
  • Primary Industrial Use Cases: Tank high/low level setpoints, temperature comfort band checking (BETWEEN), batch target match verification, and scaled pressure/flow alarm thresholds.

4.5 GUARD — Safety Interlock Gate

1. Synopsis & Execution Semantics

The GUARD block is a synchronous permissive and safety interlock gate placed inline between an upstream event source (TRIGGER, INPUT, COMPARATOR, MB_READ, or MQTT_SUB) and a downstream executor (ACTION, TON, CTU, MB_WRITE, DIRECT_WRITE, or IIoT client).

  • Pass-or-Block Event Gating: GUARD never initiates an execution pulse on its own. Instead, at the exact scan cycle when an upstream pulse arrives at In, GUARD inspects the latched process image state of GuardTag:
    • Pass (Condition True): The execution pulse propagates unimpeded out of Out within the same scan cycle (0 scan delay).
    • Block (Condition False): The execution pulse is suppressed immediately; downstream actuators remain untouched.
  • Normal vs. Inverted (NOT) Polarity: Supports active-high permissives (Negate = false, pass when GuardTag == 1) such as "Safety Door Closed = 1" and active-low fault inhibits (Negate = true, pass when GuardTag == 0) such as "Thermal Overload Fault == 0".
  • Primary Industrial Use Cases: Machine guard door interlocks, E-Stop and thermal relay permissives, Auto/Manual mode selection gates, and pump dry-run protection.

4.6 ACTION — Target Command Executor Block

1. Synopsis & Execution Semantics

The ACTION block is the terminal execution sink of a Core Rule Pipeline network. Whenever an execution pulse reaches its In connector—having cleared upstream TRIGGER, COMPARATOR, GUARD, TON, CTU, or fieldbus/cloud completion pins—ACTION performs an atomic operation on TargetTag or the runtime event subsystem.

  • Scan-Synchronous Memory Commit: Tag mutations (SET_TAG, TOGGLE_TAG, INC_COUNTER, SCALE_TAG) commit deterministically during the output update phase of the active scan cycle, ensuring predictable actuation latency across all rules.

5.1 TON — On-Delay Timer Block

1. Synopsis & Execution Semantics

The TON (Timer On-Delay) block delays the activation of its boolean output Q until the input signal In has remained continuously active (1) for the full preset duration PresetMs.

  • Sustained Activation Contract: On a rising transition of In (0 → 1), the internal elapsed counter ET begins advancing using the controller's monotonic millisecond clock while Q stays 0. Only when ET reaches PresetMs does Q transition to 1 (Q = ON).
  • Instantaneous Reset on Input Drop: If In drops back to 0 at any moment—whether mid-timing (0 < ET < PresetMs) or after Q has already energized—both ET and Q reset to 0 immediately on that scan cycle. Transient spikes or contact bounce shorter than PresetMs never reach downstream actuators.
  • Primary Industrial Use Cases: Float-switch wave and turbulence debouncing, staggered multi-motor sequential star-delta orcascade startup, conveyor jam confirmation (photo-eye blocked continuously for > 5 s), and pneumatic clamp pressure-settle delays.

1. Synopsis & Execution Semantics

The TOF (Timer Off-Delay) block energizes its boolean output Q (1) instantaneously when input In asserts 1, and holds Q = 1 for a configurable overrun duration PresetMs after In transitions from 1 → 0.

5.3 TP — Monostable Pulse Timer Block

1. Synopsis & Execution Semantics

The TP (Timer Pulse) block is a monostable, non-retriggerable one-shot pulse generator. Upon detecting a rising edge on input In (0 → 1), TP immediately drives boolean output Q to 1 for an exact, immutable duration PresetMs, then returns Q to 0.

  • Strict Non-Retriggerable Guarantee: Once a pulse is active (0 < ET < PresetMs), Q stays locked at 1 regardless of what happens on In:
    • If In drops back to 0 after just 10 ms, Q continues holding 1 until the full PresetMs elapses.
    • If In bounces 1 → 0 → 1 repeatedly during the active pulse, ET is never reset or extended—guaranteeing an exact pulse width with millisecond precision.
  • Re-Arm Requirement When In Stays High: If In is still held at 1 when ET reaches PresetMs, Q drops cleanly to 0 anyway and will not fire a second pulse until In first returns to 0 and produces a fresh rising edge (0 → 1).
  • Primary Industrial Use Cases: Volumetric solenoid dosing shots, pneumatic cylinder eject/reject kicks, baghouse dust-collector jet-pulse blowdown valves, horn chirp acknowledgments, and fixed-width reset strobes for external drives.

5.4 CYCLE_TIMER — Asymmetric Oscillator Block

1. Synopsis & Execution Semantics

The CYCLE_TIMER block is a continuous, level-enabled asymmetric square-wave oscillator (flasher). Whenever its enable input In is active (1), CYCLE_TIMER alternates boolean output Q continuously between a configurable ON phase (OnTimeMs) and an independent OFF phase (OffTimeMs), starting in either ON or OFF phase as configured.

  • Independent Asymmetric Duty Cycle: Unlike fixed 50% clock bits that require external counters and comparators to achieve short duty ratios, CYCLE_TIMER lets you combine millisecond pulses with minute/hour pauses in a single node (for example, OnTimeMs = 500 ms lubrication shot every OffTimeMs = 15 min).
  • Configurable Initial Phase (StartWithOn):
    • Start with ON (true): Immediately asserts Q = 1 for OnTimeMs on the very scan In becomes 1, then pauses Q = 0 for OffTimeMs, repeating indefinitely.
    • Start with OFF (false): Enters the OffTimeMs pause (Q = 0) first when In becomes 1, asserting Q = 1 only after OffTimeMs elapses.
  • Clean De-Energize on Disable: The instant In drops to 0, oscillation halts immediately, internal phase timers reset to 0, and Q forces cleanly to 0.
  • Primary Industrial Use Cases: Andon fault tower strobe beacons and intermittent alarm buzzers, centralized bearing lubrication pumps, greenhouse misting/fogging cycles, and periodic filter backwash agitation.

5.5 CTU & CTD — Up and Down Counters

1. Synopsis & Execution Semantics

The CTU (Count Up Counter) function block is a deterministic, rising-edge event accumulator designed for piece counting, batch totalizing, packaging quota control, and machine maintenance cycle tracking.

During each deterministic scan cycle of the SynaptiX runtime engine:

  1. Reset Priority Check (R / ResetTag): If the reset input transitions active (or is held active), the internal accumulator Current Value (CV) immediately clears to 0, and output Q de-asserts to 0 (FALSE).
  2. Rising-Edge Detection (CU): When reset is inactive and the CU input transitions from 0 → 1 (rising edge), CV increments by exactly +1 (CV ← CV + 1). Sustained HIGH levels on CU across subsequent scans do not increment the counter until CU returns to 0 and rises again.
  3. Threshold Comparison (CV ≥ PV): Output Q evaluates to 1 (TRUE) whenever CV ≥ PresetValue (PV), and 0 (FALSE) while CV < PresetValue.
  4. Tag Synchronization: CV mirrors directly into the bound CvTag (COUNTER0..COUNTER7 or VREG), and Q writes to OutputTag.
[ Post-Threshold Counting Behavior ]

If additional rising edges arrive on CU after CV reaches PV (while R remains 0), CV continues incrementing up to the 32-bit signed integer ceiling (+2,147,483,647 without wrap-around overflow), while Q remains latched at 1 until a reset occurs.

5.6 SCALE — Linear Sensor Calibration & Conversion

1. Synopsis & Execution Semantics

The SCALE (Analog Linear Scaler & Calibrator) function block transforms raw integer hardware readings (such as 0–10,000 mV, 4–20 mA loop counts, 0–4095 12-bit ADC codes, or unscaled Modbus registers) into calibrated IEEE-754 floating-point engineering units (bar, °C, m³/h, RPM, %).

Every scan cycle, SCALE evaluates the standard industrial linear transfer equation followed by optional saturation clamping:

$$y_{\text{raw}} = \text{Gain} \cdot x + \text{Offset}$$

$$y_{\text{out}} = \begin{cases} \min(\max(y_{\text{raw}}, \text{ClampMin}), \text{ClampMax}) & \text{if } \text{IsClamped} = \text{true} \ y_{\text{raw}} & \text{if } \text{IsClamped} = \text{false} \end{cases}$$

To eliminate error-prone hand calculations during field commissioning, the Inspector includes a 2-Point Calibration Calculator that automatically derives Gain, Offset, ClampMin, and ClampMax from two known physical reference points (CalibRaw1, CalibEng1) and (CalibRaw2, CalibEng2).

5.7 MATH — Combinational Arithmetic ALU Block

1. Synopsis & Execution Semantics

The MATH (Arithmetic Logic Unit) function block evaluates mathematical operations across numeric operands (INT32 and REAL / Float32) and writes the computed result to a designated destination tag (OUT).

  • IEC 61131-3 Arithmetic Operators: Supports fundamental mathematical operations: Addition (ADD), Subtraction (SUB), Multiplication (MUL), Division (DIV), and Modulo Remainder (MOD).
  • Extensible Operand Chaining ($2 \dots 8$ Pins): While conventional PLC math blocks often restrict operations to two inputs, MATH allows chaining up to 8 operands for Addition, Subtraction, and Multiplication (evaluated left-to-right: $A - B - C - \dots$). Division and Modulo strictly enforce 2 operands per industrial safety standards.
  • Dynamic Type Promotion (ANY_NUM): When set to Automatic (Auto), the block automatically promotes the calculation to IEEE-754 REAL if any operand is floating-point; otherwise, it computes in signed 32-bit integer arithmetic (INT32).
  • Division-by-Zero Protection: In event of a zero divisor ($x / 0$), the block suppresses runtime crashes, retains the last valid output state, and raises a diagnostic fault indicator.
  • Interactive Live Simulation: The configuration dialog includes a real-time ALU diagnostics test bench where engineers can inject sample values and verify formulas before commissioning to hardware.

6.1 MB_READ & MB_WRITE — Modbus RTU Communication

1. Synopsis & Execution Semantics

The MB_READ (Modbus RTU Master Read) function block enables a SynaptiX edge controller to act as an RS-485 Modbus RTU Master, actively polling external fieldbus slave instruments such as multifunction energy meters, variable frequency drives (VFDs), temperature/humidity transmitters, ultrasonic flow meters, and industrial weighing indicators.

Key runtime execution guarantees:

  • Zero Scan-Loop Blocking: All RS-485 frame transmissions, UART DMA reception, and TimeoutMs watchdogs run on a dedicated background communication worker. Slow or disconnected sensors never stall the deterministic 10 ms logic scan loop.
  • Single-Telegram Multi-Pin Extraction: A single contiguous Modbus request (StartAddress, RegCount) decodes up to 4 dynamic output pins simultaneously with per-pin word offset, data type (BOOL, INT16, UINT16, INT32, UINT32, REAL), 32-bit byte/word endianness, and linear Multiplier scaling.

6.2 DIRECT_WRITE — Hardware DO, PWM & PTO Pulse Output

  • Busy Guard (Busy = 1): Asserts Busy = 1 throughout TCP connection setup and transmission.
  • Success Handshake (Done = 1): When the remote endpoint replies with HTTP 200..299, pin Done pulses 1 for one scan cycle and updates Status (e.g. 200).
  • Network Fault Handling (Err = 1): If an HTTP 4xx / 5xx error occurs or the connection times out (TimeoutSec), Err asserts and Status reflects the HTTP error code.

5. Validation, Error Handling & Live Diagnostics

  • Strict Firmware String Length Guards:
    • Url is capped at <= 64 chars and validated for http:// or https:// scheme prefix (HasUrlError). Tip: When integrating cloud webhooks with long query tokens, route through a short local/edge gateway path (e.g., http://10.0.10.50:8080/api/v1/ingest) and place short API keys in CustomHeaders (<= 56 chars).
    • CustomTemplate is capped at <= 128 chars and checked live with JsonDocument.Parse (HasJsonError) so missing quotes or commas are caught immediately inside the dialog.
  • Re-Entrancy Protection (Busy = 1): Trigger edges arriving while Busy = 1 are safely ignored so slow cloud endpoints cannot exhaust MCU socket descriptors.
  • Live Canvas Status Pill (F8): Displays READY, TX... (in flight), HTTP 200 (#14) (last status code and cumulative request count), or ERR: <Reason>.

1. Modbus Protocol Exception Codes & Master Transport Errors

1.1 Standard Modbus PDU Exception Responses (0x01 .. 0x0B)

When a Modbus Slave (either a SynaptiX unit serving SCADA or a third-party RS-485 instrument polled by MB_READ / MB_WRITE) rejects a valid-CRC frame, it sets the MSB of the Function Code (FC | 0x80, e.g., 0x83 for FC03) followed by a 1-byte exception code:

Hex Code Standard Exception Name Root Cause in SynaptiX / Fieldbus Context Corrective Action
0x01 Illegal Function Target slave does not support the requested Function Code (e.g., sending FC06 single-register write to a sensor that only accepts FC16, or attempting write on FC02/FC04). Switch MB_WRITE from FC06 to FC16 (required for 32-bit INT32/REAL registers), or check the instrument datasheet.
0x02 Illegal Data Address Requested 0-based offset + register quantity falls outside mapped memory or crosses two distinct partitions in the Fixed SCADA Slave Map. Check for +1 (40001 vs 0x0000) addressing offset errors; split cross-partition SCADA reads into separate blocks.
0x03 Illegal Data Value Attempting to write to a hardware-locked Read-Only (RO) zone (DI, AI0..AI3, SYS_DIAG), or requesting 0 / > 125 registers in a single PDU. Ensure SCADA/Master writes target RW zones only (DO, VFLAG, VREG, VREG_RETAIN, COUNTER).
0x04 Server Device Failure Unrecoverable internal fault on the downstream slave instrument (e.g., disconnected PT100 sensor element or EEPROM fault). Inspect the physical field instrument's local display and power supply.
0x06 Server Device Busy Target device is currently executing an exclusive flash commit or held by another commissioning lease. Retry after 500..1000 ms or verify no second IDE instance holds an active write session.
0x0A / 0x0B Gateway Path Unavailable / Target Failed to Respond Upstream Modbus TCP-to-RTU gateway reached over IP, but the downstream RS-485 Slave ID did not answer on the serial trunk. Verify RS-485 Slave ID, baud rate, and A/B wiring behind the gateway.

3. Pre-Flight Compiler Validation Diagnostics (F7)

Pressing F7 (or Ctrl+F5) runs static graph verification before generating bytecode. Common diagnostics include:

Diagnostic Category Triggering Graph Condition How to Resolve on Logic Graph (Ctrl+2)
Action Missing Input (ERR_ACTION_NO_INCOMING) An ACTION block has no upstream wire connected to its Exec input pin. Connect an INPUT, TRIGGER, COMPARATOR, GUARD, or Timer/Counter output pin to ACTION, or delete the unused block.
Unconnected Trigger / Guard (ERR_TRIGGER_NO_INPUT / ERR_GUARD_NO_TRIGGER) A TRIGGER lacks an INPUT source, or a GUARD gate has no incoming signal path. Wire a valid source tag into TRIGGER, and place GUARD inline between upstream logic and ACTION.
Non-Boolean Guard Tag (ERR_GUARD_NOT_BOOLEAN) A GUARD interlock references an INT32 or REAL register instead of a BOOL tag. Bind GUARD strictly to a BOOL tag (DI, DO, VFLAG), or insert a COMPARATOR first to produce a boolean result.
Read-Only Target Violation (ERR_ACTION_READONLY_TARGET) An ACTION, SCALE, MB_READ, or MQTT_SUB attempts to write into a hardware input (DI, AI, SYS_*). Change the destination tag to a writable DO, VFLAG, VREG, or VREG_RETAIN slot.
Conflicting Multi-Writers (ERR_CONFLICTING_WRITERS) Two unconditional blocks/rules write conflicting values to the same tag on every scan, or two DIRECT_WRITE blocks claim the same DO pin. Use mutually exclusive Set / Reset conditions, consolidate into a single writer, or assign distinct DO pins.
Circular Combinational Loop (ERR_CIRCULAR_DEPENDENCY) Combinational nodes form a zero-delay feedback cycle (Tag A -> Tag B -> Tag A) with no stateful boundary. Break combinational loops through an explicit stateful block (TON, CTU) or edge TRIGGER.
Master Block on Slave Port (ERR_MB_SLAVE_PORT_CONFLICT) MB_READ or MB_WRITE is assigned to an RS-485 port configured as Modbus RTU Slave. Route the Master block to a second RS-485 port (RS-485 #2) or switch the port role back to Master in Ctrl+Shift+B.
Resource Capacity Exceeded (ERR_CAPACITY_EXCEEDED) Graph exceeds preset limits (MaxRules, 8 Timers, 8 Counters, 4 MQTT_PUB, 2 MQTT_SUB, or 4 MB_READ). Consolidate single-variable blocks into multi-pin/multi-field batch blocks, or upgrade to a higher Device Preset.

Quick Resolution Playbooks

  1. USB CDC Virtual COM Port Not Detected in SynaptiX IDE:
    • Charge-Only Cable Trap: Nearly 60% of field USB issues stem from power-only USB cables lacking D+/D- data lines. Swap to a verified data cable and inspect Windows Device Manager -> Ports (COM & LPT).
    • Exclusive Port Lock: Windows allows only one process to open a COM port at a time. Close PuTTY, ModScan, Arduino Serial Monitor, or any second IDE window before pressing F4.
  2. Modbus TCP Port 502 Connection Refused / Timed Out:
    • Confirm your workstation NIC is on the same IPv4 subnet as the SynaptiX unit (e.g., 192.168.1.x / 24) and run ping <device-ip> in PowerShell.
    • Verify no corporate firewall or managed switch ACL blocks inbound TCP port 502. Always assign a Static IPv4 (Ctrl+Shift+W or Device tab) for SCADA/TCP targets.
  3. Fieldbus Tags Flagged [STALE] During Live Debug (F8):
    • Open Ctrl+Shift+D, select the suspect channel, expand the Moxa Wire Frame Inspector, and click Read Once:
      • Zero RX bytes: Check 24V sensor supply, confirm Slave ID, and test swapping RS-485 A(+) and B(-).
      • Exception 0x02: Reduce multi-register span count or subtract/add 40001 base offset.
